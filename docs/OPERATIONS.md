# 운영 가이드

README의 개요를 읽은 뒤 사용하는 **배포·권한·보안 체크리스트**입니다. 구현 과정의 긴 대화 기록은 이 문서에 포함하지 않습니다.

## 1. 배포 구성

| 구성 | 역할 | 배포 대상 |
| --- | --- | --- |
| Vercel | React/Vite 웹앱, PWA | `dating-note.vercel.app` |
| Supabase Auth | 관리자 및 기존 viewer 로그인 | Supabase 프로젝트 |
| PostgreSQL | 후보·매칭·동의·관심 신청 | `supabase/migrations/` |
| Edge Function: `guest-share` | 개인 링크 검증, 비회원 후보 공개, 관심 신청, 푸시 | Supabase |
| Edge Function: `guest-consent` | 후보 개인별 공개 동의·거절·철회 및 개인 링크 발급 | Supabase |
| Edge Function: `guest-portal` | 신규 방문자 승인·소개자별 초대 및 개인 링크 관리 | Supabase |
| Edge Function: `create-invite` | **신규 초대 중단됨**(410 응답), 호환성 코드만 유지 | Supabase |
| Cloudinary | 이미지 업로드 | 브라우저에서 unsigned preset 이용 |

### 환경변수

`.env.example` 기반으로 다음 공개용 프런트엔드 변수를 설정합니다.

- `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`
- `VITE_CLOUDINARY_CLOUD_NAME`, `VITE_CLOUDINARY_UPLOAD_PRESET`

서버 측 Supabase Edge Function에는 `APP_URL`을 **origin만** 사용합니다. `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` 등 서버 제공 키와 푸시용 VAPID 변수는 서버에서만 관리합니다. Vercel Preview를 사용하는 경우 허용 origin과 CORS 설정을 확인합니다.

**`SUPABASE_SERVICE_ROLE_KEY`를 브라우저, 공개 저장소, `VITE_*` 환경변수에 노출하지 마세요.**

## 2. 초기 설정과 배포 순서

1. `npm install`, `npm run typecheck`, `npm run build`로 프런트엔드 검증.
2. 필요 시 `supabase/migrations/`에서 **미적용 마이그레이션만 순서대로** 적용합니다. 이미 반영한 파일을 무작정 다시 실행하지 마세요.
3. `guest-portal`, `guest-consent`, `guest-share` 등 변경된 Edge Function을 각각 배포합니다.
4. main 머지 후 Vercel 운영 화면과 Supabase 서버 API 버전이 맞는지 확인합니다.
5. 기존 후보별로 개별 동의 링크를 전달하고, 신규 방문자는 관리자에서 초대/승인을 관리합니다.

`verify_jwt = false`인 공개 Edge Function도 함수 **본문에서 관리자 JWT와 역할을 별도로 검증**해야 합니다. 후보의 동의 토큰 또는 비회원 접속 토큰을 확인하는 라우트는 서버에서 유효성을 검사합니다.

마이그레이션·Edge Function만 먼저 배포해도 실제 웹앱 화면은 자동으로 바뀌지 않습니다. 동의 필터를 먼저 배포하면 동의 기록이 없는 기존 활성 후보가 비회원 공유 목록에서 즉시 제외됩니다.

## 3. 후보 공개 동의

### 공개 기준

`guest-share`의 후보 목록 조회 **및 관심 신청 제출**은 반드시 다음을 모두 통과해야 합니다.

| 조건 | 통과 기준 |
| --- | --- |
| 후보 상태 | `활성` |
| 후보 동의 | `guest_profile_consents.management_agreed = true` 및 `decision = 'approved'` |
| 정보 동일성 | 현재 공개용 프로필 서명과 동의 당시 `profile_signature` 일치 |
| 안내 버전 | 서명에 포함된 `guest-profile-v4` 공개 정책 및 `guest-management-v1` 관리 동의 유지 |
| 동의 유지 | 후보의 자발적 철회 또는 관리자 중단이 없음 |

**자동 180일 만료는 사용하지 않습니다.** 안내문에 명시된 소개팅 주선 목적을 유지하는 동안 공개하고, 본인 철회·소개 종료·비활성 처리 시 중단합니다. 내용이 실질적으로 바뀌면 새 동의가 필요합니다. 주선 목적을 달성해 불필요해진 원본 프로필 정보는 별도로 삭제 또는 적법한 근거에 따라 정리해야 합니다.

### 동의 링크 관리

- 관리자 후보 상세의 **🔐 개인정보 동의 관리**에서 개인별 동의 링크를 만듭니다. 기존 이름 표기와 관계 구분으로 직접 아는 사람/건너건너 소개받은 사람을 관리하므로 **중간 주선자 이름은 별도로 수집하지 않습니다.**
- 동의 페이지 맨 앞에서 **‘주선자에게만 맡기기’**(내부 보관만 동의)와 **‘소개팅 기회 넓히기’**(이름·사진 제외한 프로필을 승인된 방문자와 개인 링크 이용자에게 공개)를 쉬운 말로 설명합니다. 아래에서는 실제 정보 항목, 목적·기간·거부권을 확인하고 별도로 동의합니다.
- 후보는 관리자가 이미 보관한 **이름·사진 등 정보의 항목과 사진 장수** 및 비회원에게 나갈 **출생연도·키·지역·직업·이상형·특징** 등을 따로 확인합니다. 실제 이름·사진은 링크만 가진 타인에게 노출되지 않도록 후보 동의 페이지에 직접 표시하지 않습니다. 후보 관리 목적 **수집·이용 동의(참여 시 필요)**와 **비회원 공개 동의(선택)**를 구분합니다. 공개에 체크하지 않아도 관리자 보관만 선택해 제출할 수 있어야 합니다.
- 링크는 후보가 알고 있는 연락 수단으로 전달합니다. **링크를 가진 사람과 실제 후보 본인이 같다는 자동 인증은 없습니다.**
- 공개만 거부·철회하면 관리 목적 보관 동의는 유지하고, 비회원 목록에서 제외합니다. **전체 거절·내부 보관 동의 철회 시 `deletion_requested_at`을 기록해 관리자에게 삭제 처리를 요청**합니다. 자동으로 원본 DB 행·Cloudinary 파일이 삭제되지는 않습니다.
- 관리자는 즉시 비회원 공개를 중단하거나 링크를 재발급할 수 있습니다. 링크를 재발급하면 이전 링크가 무효화됩니다.
- 후보는 동의 링크에서 출생연도·키·거주지·직업·이상형·특징을 직접 수정하고, 수정한 최종 공개 프로필에 대해 보관·이용 및 공개 여부를 함께 선택할 수 있습니다. 성별·관계 구분·이름·사진·매칭 이력은 주선자가 수정합니다. 한 화면에서 수정·동의 저장을 원자적으로 처리하며, 관리자 변경·만료된 개인 링크나 다른 탭의 오래된 화면은 거부합니다.
- 개인정보 수집·이용 및 공개 안내는 필수 고지의 핵심 요약을 항상 표시하고, 상세 설명은 접어서 볼 수 있습니다. 보관·이용 동의와 선택적 프로필 공개 동의는 구분하고, 동의하지 않기·개인정보 삭제 요청·철회 기능은 유지합니다.
- 이전에 동의한 정보가 바뀐 경우 기존 링크에서 변경 내용을 확인하고 재동의할 수 있습니다.
- `guest_profile_consent_events` 테이블에 비회원 공개 승인 당시의 프로필 사본, 관리자 보관 동의 상태 및 변경·철회 이력을 기록합니다. 실제 이름과 사진 URL을 감사 기록에 복사하지 않고, **보관 항목과 사진 수량**만 남깁니다. 해당 이력도 개인정보이므로 보호하고 불필요해지면 정리합니다.

### 기존 viewer 계정은 별개

**신규 사용자 초대 기능은 중단**되지만 기존 viewer 로그인 계정은 남아 있습니다. 기존 `people_public` 뷰에도 **활성 + 내부 관리 동의 + 비회원 공개 선택 동의 + 공개 프로필 내용 일치** 조건을 적용하여, 선택 동의를 하지 않은 후보는 viewer에게도 보이지 않습니다. 관리자 로그인은 내부 관리를 위해 기존대로 유지합니다. viewer 계정을 완전히 비활성화하거나 삭제하는 작업은 별도의 결정이며 이번 변경에서는 수행하지 않습니다.

**중간 주선자에게 받은 이름·사진도 후보 본인의 동의로 간주할 수 없습니다.** 출처 확인 요청에 답할 수 있도록 기록하고, 후보가 내부 관리 동의를 거절하거나 철회하면 불필요한 보관 정보를 정리해야 합니다. 기존 viewer가 동의 없이 열람하던 경로는 `20261119060000_guard_legacy_viewer_consent.sql`에서 차단합니다.

## 4. 로그인 없는 비회원 초대·승인 및 개인 링크

- 일반 소개팅 주소: `/i-need-money`. 추천인 링크는 `#invite=<서명 토큰>`을 포함합니다. 로그인이나 PWA 설치는 필요하지 않습니다.
- **기존 DB 후보**는 각각의 `/consent/:token` 링크에서 자신의 공개 범위와 관리 동의를 선택합니다. 관리 동의가 있으면 **추가 관리자 승인 없이** 개인 열람 링크가 발급됩니다. 공개 선택동의 거절 여부는 본인의 열람 권한과 독립적입니다.
- **새 방문자**는 이름과 소개 경로를 제출한 뒤 관리자의 승인을 기다립니다. 추천인 초대 링크를 사용했다면 소개자는 자동 기록합니다. 미승인 방문자에게 후보 정보는 반환되지 않습니다.
- 승인/동의 후 발급되는 `/i-need-money#key=<개인 토큰>`은 **최초 브라우저 등록 수단**입니다. 첫 이용 브라우저를 자동 등록한 뒤에는 해당 브라우저의 별도 인증키로 접속합니다. PC 등 다른 브라우저에서는 기존 인증 브라우저에서 9자리 연결번호를 승인해야 합니다. 링크를 받은 사람이 실제 당사자인지는 처음 접속만으로 증명되지 않으므로 신뢰하는 경로로 전달해야 합니다.
- 중간 주선자별 초대 링크는 여러 사람에게 공유할 수 있고 만료일·횟수 제한이 없습니다. 새 방문자는 **한 명씩 개별 승인**받아야 합니다. 중간 주선자의 후보 직접 등록 기능은 다음 단계로 남겨 둡니다.
- 신규 방문자의 이름은 동일인 증명이 아닙니다. 기존 `people` 테이블에 있는 `김지영 건너` 등 관리용 이름은 수정하지 않고, 후보별 DB ID로 연결합니다. 이름이 같아도 자동 병합하지 않습니다.
- 후보 열람·관심 신청은 서버에서 개인 링크 해시, 승인 및 취소 상태를 검사합니다. 동의가 유효한 후보만 반환하고, 기존 공통 접속코드로는 더 이상 열람할 수 없습니다.
- 주선비 문구는 선택적 안내 한 줄만 두며, 필수 체크박스나 결제 기능이 아닙니다.
- 개인정보 공개 안내 대상이 바뀌어 공개 동의 버전은 `guest-profile-v4`입니다. 기존 버전 동의만 있는 후보는 재동의 전까지 외부 후보 목록에 표시되지 않습니다.

## 5. 배포 전 확인 목록

- [ ] 관리자 로그인·후보 편집·매칭·신청 처리 화면 정상 동작
- [ ] 사용자 초대 메뉴 미표시 / `create-invite` 신규 초대 요청 거절 확인
- [ ] 아직 동의한 후보가 없으면 `browse` 응답과 기존 viewer의 `people_public` 조회 모두 비어 있음
- [ ] 후보별 동의 링크에서 이름·사진·연락처·매칭 이력이 반환되지 않음
- [ ] 비회원 공개 선택동의 미체크 + 관리자 보관 동의 체크 → 저장 성공, 비회원 목록 미노출
- [ ] 이름·사진 포함한 내부 관리 항목 안내 / 후보 본인에게 실제 이름·사진을 확인할 경로 안내
- [ ] 전체 거절/관리 동의 철회 → 외부 비공개 및 관리자 삭제 요청 표시
- [ ] 후보 미동의/거절/철회 시 비회원 목록에서 즉시 제외됨
- [ ] 후보 공개 항목 수정 후 재동의 전까지 제외, 재동의 시 재노출
- [ ] 관심 신청 API로 비공개 후보의 ID를 강제 전송해도 거부
- [ ] 새 동의 링크 재발급 시 이전 링크 무효화
- [ ] 현재 프로필 서명·동의 문구 버전 불일치 시 승인 거부
- [ ] 동의 감사 테이블 RLS 활성, anon/authenticated 조회 권한 없음
- [ ] 공통 접속코드로 후보 열람 불가, 미승인/차단된 개인 링크로 후보 열람·관심 신청 불가
- [ ] 기존 후보는 동의 후 별도 승인 없이 열람, 신규 방문자는 승인 전까지 열람 불가
- [ ] 기존 브라우저는 재접속 시 별도 조작 없이 열람, 다른 브라우저는 9자리 연결번호 승인 필요, 추천인 링크로 들어오면 소개자 자동 기록
- [ ] 초대 중단 후에도 기존 관리자 로그인, 비밀번호 재설정 호환 확인
- [ ] PWA 업데이트 시 최신 웹앱 버전이 적용되는지 확인

## 6. 로컬 테스트와 문제 해결

```bash
npm run typecheck
npm run build
npm run test:auth
npm run test:app
npm run docs:check
```

**폰에서 개발 서버:** PC와 폰을 같은 Wi-Fi에 연결하고 `npm run dev -- --host 0.0.0.0`으로 실행합니다. 컴퓨터의 로컬 주소로 접속할 때는 방화벽 설정을 확인합니다.

**Samsung Internet/Chrome PWA가 예전 화면을 표시:** 열려 있는 관련 탭을 모두 닫고 다시 열어보세요. 앱 설치/서비스워커 캐시 정책에 따라 구버전 화면이 남을 수 있습니다.

**CORS 오류:** 운영 도메인과 현재 Preview origin이 Edge Function의 허용 목록에 있는지, POST 요청의 실제 응답에 CORS 헤더가 붙는지 확인합니다.

**데이터가 비어 있음:** `guest-share` 서버에 후보별 동의 필터가 적용된 뒤 **동의한 후보가 0명이면 정상 동작**입니다. 우선 관리자에서 후보별 동의를 확보한 뒤 확인하세요.

**데이터 보안:** `people.note`가 비회원 ‘특징’ 항목으로 공개되므로, 관리 전용 메모나 외부에 보이면 안 되는 내용은 입력하지 마세요. `people` 행을 삭제하더라도 Cloudinary 이미지가 별도로 남을 수 있으므로 실제 저장소의 삭제도 확인해야 합니다.

## 추가 동의 사항 (관리자 보관 / 공개 분리)

- **개인정보 수집·이용:** 후보의 이름, 사진, 기본 프로필, 이상형, 상태, 매칭 기록을 관리자용으로 보관·이용하는 목적과 기간을 명시합니다. 후보 관리에 참여하려는 경우 필요한 동의이며, 거부하면 참여하지 않아도 됩니다.
- **제3자 제공·비회원 공개:** 별도 **선택동의**입니다. 관리자 관리에만 동의해도 저장하고, 비회원 페이지에는 표시하지 않습니다. 실제 공개는 두 동의가 모두 유효할 때만 허용합니다.
- **이미 보유한 정보:** 지인이나 중간 주선자를 통해 전달받은 정보라 해도 동의 여부를 별도로 확인해야 합니다. 이후에 받은 동의가 최초 수집 시의 법적 근거 문제를 소급해서 해결하는 것은 아닙니다.
- **삭제 요청:** 후보 전체 거절·철회 시 동의 관리 화면에 요청 일시를 표시합니다. 해당 행, 연관 매칭 이력, 이미지 저장 위치 등을 확인하고 담당자가 실제 파기해야 합니다. 처리 기한과 고지 방법 등은 운영자가 별도 관리합니다.
- **시스템 마이그레이션:** `20261119053000_separate_management_public_consent.sql`은 기존 승인만으로 관리 동의를 추정하지 않고 기본값을 `false`로 두며, 동의 변경/삭제 요청은 트리거로 감사 기록을 남깁니다.

## 7. Supabase 무료 프로젝트 정기 점검

- `public.keepalive_ping()`은 개인정보 테이블을 읽지 않는 최소 권한의 `SECURITY INVOKER` 함수입니다. `anon` 역할에만 EXECUTE를 부여했으며, 공개용 API 키만 사용합니다.
- `.github/workflows/supabase-keepalive.yml`이 GitHub Actions에서 매일 세 번 (한국시간 **09:17 / 15:17 / 21:17**) `POST /rest/v1/rpc/keepalive_ping`를 호출합니다.
- 점검 성공 시 반환값은 `true`입니다. 네트워크 오류나 응답 이상은 최대 3회 재시도한 뒤 작업을 실패 처리합니다.
- 수동 점검: GitHub 저장소 **Actions → Supabase DB 정기 점검 → Run workflow**. 실행 기록이 녹색인지 확인합니다.
- **Supabase Free 일시정지 방지를 보장하지 않습니다.** Supabase는 일주일간 실제 사용량이 너무 적으면 정지할 수 있으며, 확실한 방지는 유료 플랜뿐입니다.
- **GitHub 공개 레포의 예약 워크플로는 60일간 저장소 활동이 없으면 자동 비활성화될 수 있습니다.** 이 경우 Actions에서 다시 활성화하거나, 별도의 외부 스케줄러를 이용하세요. 자동 점검 요청 자체가 레포 활동으로 인정되는 것은 아닙니다.
- 프로젝트가 이미 일시정지되었다면 자동 호출로 복구되지 않으므로 Supabase Dashboard에서 재개해야 합니다.
- `keepalive_ping`은 서버 비밀키·후보 개인정보에 접근하지 않습니다. 작업 파일에 `service_role`이나 비밀키를 넣지 마세요.

## 7. GitHub 머지 후 Supabase 배포 자동화

`.github/workflows/deploy-supabase.yml`은 main에 Supabase 코드·마이그레이션 변경이 있을 때 작동하는 배포 절차입니다. **기본값은 비활성**입니다. 다음 설정을 마친 뒤에만 운영 배포가 실행됩니다.

1. GitHub 저장소 **Settings → Secrets and variables → Actions → Secrets**에 `SUPABASE_ACCESS_TOKEN`을 등록합니다. 이 값은 Supabase에서 발급한 권한 제한 가능한 Personal Access Token입니다. 코드나 Vercel 브라우저 변수에 넣지 마세요.
2. 같은 곳의 **Variables**에 `SUPABASE_DEPLOY_ENABLED=true`를 추가하면 변경된 Supabase 함수가 자동 배포됩니다. 배포 워크플로를 수동 실행하는 것도 가능합니다.
3. DB 마이그레이션 자동 배포를 사용하려면 GitHub Secrets에 `SUPABASE_DB_PASSWORD`를 추가해야 합니다. **이력 불일치를 모두 복구하기 전에는 `SUPABASE_DB_DEPLOY_ENABLED`를 절대 true로 설정하지 마세요.**

### 마이그레이션 안전장치

현재 오래된 마이그레이션 파일의 버전과 실제 Supabase 적용 이력이 여러 개 달라서, **DB 자동 배포 기능은 의도적으로 잠가 둔 상태**입니다. 메인에 새 DB 마이그레이션이 포함된 채 머지되더라도 `SUPABASE_DB_DEPLOY_ENABLED`가 켜지지 않았으면 워크플로가 명시적으로 실패하며 **Edge Function도 배포하지 않습니다**. DB 변경 없이 함수만 변경할 때는 함수만 배포합니다.

나중에 이력을 대조·복구한 후 `SUPABASE_DB_DEPLOY_ENABLED=true`로 설정하면, 스크립트 `scripts/check-supabase-migration-history.mjs`가 현재 저장소와 운영 DB의 과거 이력을 검사합니다. 버전 불일치가 하나라도 발견되면 `supabase db push` 전에 중단합니다. 이력 기록을 맞추기 위해 과거 DDL을 운영 DB에 재적용하거나 무작정 `supabase migration repair`를 실행하지 마세요.

**순서:** 마이그레이션 검증·배포 → 모든 Edge Functions 배포. 공개 함수 `guest-share`, `guest-portal`, `guest-consent`는 `supabase/config.toml`에 `verify_jwt=false`를 유지하고 함수 내부에서 자체 자격 검증을 합니다.

운영 배포가 성공했더라도 Vercel의 캐시된 구형 PWA가 새 인증 방식으로 자동 전환되지 않을 수 있습니다. 기존 이용자는 앱을 완전히 종료했다가 다시 접속하고, 오래된 개인 링크 접근 화면이 계속 나오면 새 버전에서 재접속해야 합니다.
